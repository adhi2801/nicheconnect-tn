# Backend research: the world's best practice, ours against it, and what we do next

**For:** whoever builds or judges the backend, and `docs/BACKEND_COMPLETE.md`, which turns each "next" below into an item. **Written 6 November 2026**, at Adhi's request ("innovation research, novelty research, better than competitors, world class research with depth ... backend, database, connection, and whatever there is"). Every claim about our system was read from the code on `main` that day; every claim about the outside world carries its source and the date it was read.

**What this file is not:** the product research. What brands and creators need, and what competitors offer them, is `docs/COMPETITIVE_LANDSCAPE.md` and `docs/BILLION_DOLLAR_GAP.md`. This file is the engineering underneath: how the leaders build an API, a database, its connections, its reliability, its security and its learning, and where ours stands.

**How to read each section:** *The leader* (what the best publish, with the source), *Ours today* (from the code), *Next* (a proposed item, never built before its approval, `CLAUDE.md` section 5), and, where we can go further than anyone, *Ahead*.

**Source quality, said plainly:** where only a secondary write-up was found, the line says so. Numbers from vendors are their claims, not measurements of ours.

---

## 1. The API contract

### 1.1 Errors
- **The leader:** RFC 9457, *Problem Details for HTTP APIs* (IETF, July 2023), the one error format clients can parse without reading our docs.
- **Ours today:** every error is RFC 9457 problem details (`app/core/errors.py`); one format everywhere.
- **Holds.** Nothing next.

### 1.2 Retrying safely
- **The leader:** Stripe: an `Idempotency-Key` header makes every create safe to retry; API v2 extends it to every POST and DELETE (Stripe docs, "API v2 overview", read 6 November 2026). Stripe's engineering post on idempotency (22 February 2017) is the reference design. Whether keys live 24 hours or longer differs between secondary sources; Stripe's own docs are the authority.
- **Ours today:** `Idempotency-Key` on the creates where a repeat would cost someone (25 files: applications, invitations, offers, notes, shipments, lists, deletion and more), stored in Valkey (D-048).
- **Next:** a test that walks every POST and DELETE in the contract and fails on one that a client cannot safely retry, the way item 100's test walks every route for strangers. **Ahead:** no creator marketplace publishes this guarantee; we can state it in the API's own documentation.

### 1.3 Changing the API without breaking anyone
- **The leader:** Stripe pins each account to a dated version (`Stripe-Version: 2024-10-28`), ships monthly versions that only add, and isolates old behaviour behind version gates at a fixed cost (Stripe, "APIs as infrastructure: future-proofing Stripe with versioning", 15 August 2017; Stripe versioning docs, read 6 November 2026).
- **Ours today:** `/api/v1`, a committed contract (`docs/api/openapi.json`) that tests hold the app to, and generated frontend types that CI checks. A 12-month never-break rule with a breaking-change check was proposed in the world-bar pass and is **not approved**.
- **Next:** the breaking-change check in CI (a contract diff that fails on a removed field, a narrowed type or a new required input), which three apps will depend on. The dated-version scheme waits until a client outside our own apps exists.

### 1.4 Telling clients their limits
- **The leader:** the IETF's `RateLimit` and `RateLimit-Policy` fields (draft-ietf-httpapi-ratelimit-headers-11, 23 May 2026): still an Internet-Draft, not an RFC, expiring 24 November 2026.
- **Ours today:** every public route limited (constraint 4); `Retry-After` on every refusal.
- **Next:** send both fields, labelled as the draft's, so a client can slow down before it is refused. **(decision)**, as proposed in the world-bar pass; the trigger to call it final is the RFC.

### 1.5 The contract's own format
- **The leader:** OpenAPI 3.2.0 (OpenAPI Initiative, 23 September 2025): the `QUERY` method, streaming and sequential media (`itemSchema`), hierarchical tags, deprecated security schemes; non-breaking from 3.1.
- **Ours today:** 3.1.0, generated by FastAPI.
- **Next:** none until FastAPI generates 3.2; the trigger is its release notes. Streaming answers (the brief drafter's progress) would then be described, not hand-documented.

### 1.6 Events to other systems
- **The leader:** Standard Webhooks: `webhook-id` (stable across retries, for deduplication), `webhook-timestamp`, `webhook-signature` (`v1,` + HMAC-SHA256 over id, timestamp and body), a replay window around 300 seconds (secondary sources; the specification itself at standardwebhooks.com is the authority).
- **Ours today:** no outbound events. Agencies and larger brands (item 72, `BILLION_DOLLAR_GAP.md` section I) will want deal and payment-status events in their own tools.
- **Next:** when the first agency asks, events signed to Standard Webhooks, with a delivery log each side can read. **Ahead:** a deal event carries its deal record seal, so the receiver can verify it against `DEAL_RECORD_VERIFY.md` without trusting us.

## 2. The database

### 2.1 PostgreSQL 18 (released 25 September 2025)
Read in the PostgreSQL 18 release notes and secondary summaries (Neon, Better Stack, read 6 November 2026):

| Feature | What it gives | Ours |
|---|---|---|
| Asynchronous I/O (`io_method`) | Sequential and bitmap scans and vacuum issue reads ahead | Not configured: the default (`worker`) runs. **Next:** measure `worker` against `io_uring` on the production image's kernel before launch, with `scripts/measure_performance.py`; vendor speed claims are unverified |
| `uuidv7()` | Time-ordered keys, index-friendly inserts | **Used** on every table since 26 September (D-047) |
| B-tree skip scan | A multi-column index serves a query that skips its leading column | Not reviewed. **Next:** read every composite index against its queries; skip scan may let two indexes become one |
| Virtual generated columns (the default kind) | Computed on read, no storage | Stored ones chosen for matching's words (D-173), because reading is the hot path |
| Data checksums on by default | Silent disk corruption is detected | Production is RDS; **Next:** confirm RDS reports checksums on |
| OAuth authentication | Database logins from an identity provider | Not needed: the app's login is a role with a SCRAM password set at release (D-100) |

### 2.2 Vectors
- **The leader:** pgvector 0.8 added iterative index scans: a filtered approximate search keeps scanning until enough rows match, capped by `hnsw.max_scan_tuples` (20,000 by default), off unless switched on (pgvector README; Nile, 5 November 2024).
- **Ours today:** pgvector 0.8.7 on PostgreSQL 18 locally; no vector index (`database.md` section 5): exact search inside the structural filter, which is right at pilot scale.
- **Next:** when a table needs HNSW (the trigger in `database.md` section 5), switch iterative scans on with the index, or a city-and-niche filter will silently return short lists. Written into the trigger now so it is not rediscovered.

## 3. Connections

- **The leader:** the PostgreSQL project's starting point, published on the HikariCP wiki ("About Pool Sizing", read 6 November 2026): connections ≈ (database cores × 2) + effective spindles, the spindles zero when the working set is cached; then load-test around it. More connections than that make throughput fall, not rise.
- **Ours today:** 5 connections and 10 overflow per process (`app/core/config.py`), a 503 with `Retry-After` when the pool is exhausted (D-093), a statement timeout on every connection. One process held about 400 people (D-093).
- **The gap:** the number that matters is the total: processes × containers × (pool + overflow) against the database's cores and `max_connections`. Autoscaling (item 88) multiplies it, so the total grows with scale until the database thrashes.
- **Next, in order:** (1) a startup check and a test that the configured total, at the autoscaler's maximum, stays within the formula for the planned instance; (2) a connection pooler before autoscaling goes past what the formula allows. PgBouncer 1.25 in transaction mode needs `max_prepared_statements` above zero for psycopg's prepared statements (PgBouncer 1.25 docs; a February 2026 pgsql-general thread shows the failure when it is not); RDS Proxy is the managed alternative, at the cost of connection pinning on session state. **(decision)** between them, measured, when item 88 is built.

## 4. Reliability

### 4.1 Objectives, budgets and alerts
- **The leader:** Google's SRE practice: each user journey has an objective; the error budget is what the objective allows to fail; alerts fire on the burn rate over two windows at once (a fast pair, 1 hour and 5 minutes at 14.4 times the sustainable rate, which spends 2% of a month's budget in an hour; a slow pair, 6 hours and 30 minutes at 6 times) so they are neither noisy nor late; and an error budget policy, agreed in advance, says what stops when the budget is spent (*The Site Reliability Workbook*, "Alerting on SLOs"; secondary summaries read 6 November 2026).
- **Ours today:** latency budgets per route, measured locally (`docs/PERFORMANCE.md`); availability set in the world-bar pass (D-166); tracing and error tracking built (items 2, 3). No objective is measured in production, because nothing is deployed, and no burn-rate alert or budget policy exists.
- **Next:** objectives for the five journeys that matter (sign in, publish a campaign, apply, agree a deal, mark paid), burn-rate alerts on each from the traces item 89 will collect, and a one-page error budget policy for both founders to sign. **Ahead:** publish the objectives and a monthly report beside the deal record's verification page; no creator marketplace publishes its reliability.

### 4.2 Background work
- **The leader:** durable execution: a workflow's progress is checkpointed so a crash resumes it, never repeats a step. DBOS does this inside PostgreSQL (DBOS Transact; monthly release notes April to July 2026 add step timeouts, queryable workflow attributes and enqueueing from triggers).
- **Ours today:** DBOS for background jobs (D-060).
- **Next:** cooperative step timeouts on every job that calls outside (WhatsApp, the Claude API, S3), so a hung call cannot hold a worker; queryable attributes to replace any hand-written "find stuck jobs" query.

### 4.3 Valkey
- **The leader:** Valkey 9.0 (generally available 21 October 2025): hash field expiration (its most requested feature), atomic slot migration, multiple databases in cluster mode.
- **Ours today:** Valkey 9.1.2 locally, for rate limits and idempotency keys.
- **Next:** where a key holds several fields with different lifetimes (an idempotency record and its lock), per-field expiry instead of separate keys. Small; worth doing when that code next changes.

## 5. Observability
- **The leader:** OpenTelemetry's database semantic conventions were marked stable in 2025 (version 1.33.0; Grafana, June 2025; the conventions' migration guide), with instrumentations moving to the stable attribute names behind `OTEL_SEMCONV_STABILITY_OPT_IN`.
- **Ours today:** OpenTelemetry in the app (item 3, D-094); where traces go waits on hosting (item 89).
- **Next:** emit the stable database attributes (opt in to `database`) before item 89, so dashboards built on them never need rewriting.

## 6. Security
- **The leader:** OWASP ASVS 5.0.0 (2025): reorganised and reworded, levels rebalanced so Level 1 is reachable; mappings through OWASP's Common Requirement Enumeration.
- **Ours today:** `security.md` is mapped to ASVS 5.0 (D-166); passkeys built (item 79, off until the domain); admins with a second factor (item 101); step-up codes for risky changes (item 82).
- **Next:** the Level 2 walk, requirement by requirement, as an item with its evidence column, and Level 3 for login, sessions and the deal record. Admins on passkeys was proposed in the world-bar pass and is **not approved**.

## 7. The runtime
- **The leader:** Python 3.14's free-threaded build is officially supported (PEP 779, accepted for 3.14) but opt-in, with a 5 to 10% single-threaded cost and uneven wheels outside the scientific core (secondary summary, read 6 November 2026).
- **Ours today:** Python 3.14 with the GIL (D-072).
- **Next:** none now. **Trigger:** every dependency with C code (psycopg, pydantic-core, the embedding stack) ships free-threaded wheels, and a load test shows more people per container. Until then the gain is unproven for us.

## 8. Learning from the platform
- **The leaders:** Fiverr's investor materials describe matching rebuilt around a knowledge graph of the client, the talent, the scope and the order, and a graph neural network that cut cancellations by 7% against their previous model in first tests (Fiverr investor relations, read 6 November 2026). Airbnb scores every reservation for risk before it is confirmed, from hundreds of signals (Airbnb Trust and Safety page, 2021 archive; no 2025 primary source found). Upwork lets freelancers see whether a client's payment method is verified and their hiring history (Upwork, "Upwork vs. Fiverr", 2026).
- **Ours today:** hybrid retrieval built (D-167, D-173); the learned reranker waits on real outcomes; brands' payment and delivery records shown beside every match (D-027, D-038); verified brand domains (item 74); look-alike brand names flagged (item 75).
- **Next:** (1) measure what Fiverr measured: cancellations and unfinished deals per match list, from step 2's impressions, as the reranker's second gate beside NDCG; (2) **a check on each deal before it is agreed**, from records only we hold: a brand's days to pay and disputes, a creator's delivery record, a domain verified or not, a look-alike name, a first deal between the two; shown to both sides as facts, never as a score that refuses anyone (`trust-and-safety.md`: flags, never verdicts). **Ahead:** Airbnb scores one side for its own protection; ours shows both sides the same facts about each other.
